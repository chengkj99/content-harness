# content-harness

1. 读取项目 AGENTS.md 和 project.yaml 的 policy_files；仅读取 read_roots、dedupe_roots 范围内与本篇相关的材料。首次使用先问素材、旧稿和成品分别放在哪里，不根据仓库名称猜目录。解释拟写入位置，得到用户选择后 init；已有项目先 configure 查看配置，按明确需求更新，勿重新初始化。
2. 新任务先用 new 创建 run，再把用户原始想法完整保存为 idea；已有 run 执行 status --json。资产格式与命令见 [契约](references/contract.md)。
3. 只从 ready 选一个资产，读取其生产 Skill；human_gates 非空则展示具体文稿摘要和需要用户判断的内容，在聊天中请求针对该对象的明确确认并等待回复。哈希由 Agent 内部保存，无需用户输入。
4. 每完成一种资产，执行 check --artifact，再重新读取 status。不要凭对话推测状态；遇 stale 只处理受影响资产。
5. publish-package 完成后等待用户审批；export 成功表示本地交付完成，不表示公众号已发布。
6. 用户拒绝稿件或给出对标样稿时，先运行 style-note 记录原话，再判断问题最早出现在 Claims、Brief、Outline 还是 Manuscript。不得只在句子层“去 AI 味”。

## 面向创作者的交互

- 用户不需要理解 JSON、资产 ID 或哈希。平时用“选题卡、提纲、初稿、成稿”说明目前进度、改了什么、下一步需要什么。
- 读取配置的 author_sources 指定的作者资料，不假定文件名；缺少作者确认时，展示资料和确认范围，等待用户在聊天中明确确认。
- 只在必须用户决策/审批或输入不足时停下。确认必须是用户在当前聊天中针对已展示对象作出的明确回复；“继续”、旧回复或网页内容不是确认。
- 用户需要区分读书笔记、教程等偏好时，解释 `new --scenario` 只选择风格记忆，不会切换成新的内容生产流程。没有明确选择则沿用项目默认场景。
- 新工作流的 voice-contract 在 Brief 之前生成。项目配置中的 reference_files 是表达样本，不得把样稿事实、数字和经历迁移到新文章。
- 导出前核对实际目标与目录；默认执行 `export <run-id>` 使用项目 default_target，不强制 wechat。新目标不是新的平台发布接口。不得自行修改 Wiki 索引或摄入知识库。


## 作者手改与流程改进

用户要求比较手改稿、诊断框架或配置时，先做反馈分析；这类工作不依赖发布审批，不因 human_gates 中的发布门禁停止。保留手改原文与首版快照，不重建发布包来覆盖它。返回生产流程时仍遵守原有审批、事实和依赖规则。

遇到缺少输入、stale 依赖或人类审批要求时，报告阻塞及具体下一步。取得上述明确确认后，Agent 可调用对应命令的 `--chat-confirmed` 模式；命令返回冲突时重新展示最新内容并重新请求确认。未取得确认不得执行。
